#### 2. 架构职责明确

**信号网关（gb28181-gateway）- 纯 SIP 协议处理：**
```
职责：
├── 设备注册/注销
├── 心跳保活
├── MESSAGE 消息（目录/状态/报警）
├── INVITE 处理（简化，仅解析设备 SDP）
├── 响应处理（提取设备 SSRC）
└── 推送 Hook 到 API 项目

核心特性：
✅ 不涉及任何 ZLM 逻辑
✅ 不管理 SSRC（由 API 项目数据库管理）
✅ 不分配媒体端口（由 API 项目 ZLM 管理）
✅ 使用 C 扩展原生 SDP 解析器（\ExoSip::parseSdp）
```

**API 项目（gbvr-iot）- 业务逻辑与媒体管理：**
```
职责：
├── 接收网关 Hook（register/catalog/media_ready/voice_invite）
├── ZLM 集成（端口分配、SSRC 管理、流控制）
├── 数据库管理（设备、通道、SSRC、会话）
├── 业务 API（设备 CRUD、流控制、PTZ、回放）
└── 通过 Redis 下发命令到网关

核心特性：
✅ 完整的 ZLMClient SDK（支持 tcp_mode）
✅ SSRC 数据库管理（UNIQUE 约束）
✅ 媒体端口分配与释放
✅ 流会话全生命周期管理
```

### 五、关键技术方案

#### 1. SSRC 管理方案

**问题：** 原代码 SSRC 硬编码为 "0100000001"，多路流冲突

**解决方案：**
```
数据库管理：
├── device_channels.ssrc UNIQUE 约束
├── 首次分配：自动生成10位数字
├── 持久化存储：重启不变
└── 冲突检测：数据库层自动处理

流程：
1. API 从 device_channels 获取/生成 SSRC
2. API 分配 ZLM 端口（tcp_mode 支持）
3. API 通过 Redis 下发命令（带 ssrc/port/tcp_mode）
4. 网关使用 API 提供的参数构建 SDP
5. 设备响应后，API 更新 ZLM 的 device_ssrc
```

#### 2. RTP 传输模式支持

**tcp_mode 参数：**
```
0 = UDP           // 局域网推荐，延迟低
1 = TCP 被动      // 公网推荐，NAT 友好
2 = TCP 主动      // 特殊场景
```

**配置：**
```php
// config/zlm.php
'default_tcp_mode' => 1  // 默认使用 TCP 被动
```

**应用流程：**
```
1. Controller 选择 tcp_mode
2. 调用 ZLM openRtpServer($stream_id, $tcp_mode)
3. 获得端口号
4. 通过 Redis 传递给网关
5. 网关在 SDP 中使用（TCP/RTP/AVP）
```

#### 3. 媒体流就绪处理

**关键 Hook：media_ready**

```php
// 网关推送（handleInviteResponse）
Hook 数据：
- device_ssrc   // 设备实际使用的 SSRC（从 SDP 提取）
- device_ip     // 设备媒体 IP
- device_port   // 设备媒体端口
- protocol      // RTP/AVP 或 TCP/RTP/AVP
- call_id       // SIP 会话 ID
- dialog_id     // SIP 对话 ID

// API 处理（GBServerHockController::handleMediaReady）
1. 根据 call_id 查找会话
2. 调用 ZLM updateRtpServerSsrc($stream_id, $device_ssrc)
3. 更新数据库 device_ssrc
4. 获取播放地址
5. 更新会话状态为 active
```
